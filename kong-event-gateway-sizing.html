Guide Principles

What this model does — and doesn't — tell you

Tested, not published

All numbers trace back to a single informal load test ("Kiburi Rust Perf") run for a prior customer engagement — not an official Kong benchmark. Treat outputs as a starting point, not a committed number.

Fixed node size

Every scenario ran on the same 4 vCPU / 16GB instance. The tool shows observed utilization within that box — it does NOT tell you the minimum viable instance, since smaller nodes were never tested.

Scale-out, not scale-up

Event Gateway is stateless and horizontally scalable behind an LB — any instance can serve any backend broker. Plan capacity in number of 4vCPU/16GB instances, not bigger boxes.

Scale-out triggers
Proxy CPU utilization approaching provisioned vCPU (test showed up to 3.86 vCPU used on a 4 vCPU node under JSON validation at 100MB/s)
Consume-side throughput approaching the policy's ceiling — encryption roughly halves consume throughput vs. baseline
p99 latency spikes disproportionate to p50 — seen with Headers and Encryption scenarios even at moderate load
Known gaps to re-verify
JSON Schema Validation at 100MB/s showed p99 ≈ 404ms — a ~27x jump vs. the 50MB/s test (15ms) with no explanation in the source data. Treat as a likely anomaly, not a real ceiling.
Header Modification was only tested at 50MB/s — no higher-throughput data point exists
Kafka brokers were co-located on one shared VM in the test, which may have introduced contention not present in your topology
Event Gateway is confirmed stateless — safe to scale horizontally behind a standard LB
